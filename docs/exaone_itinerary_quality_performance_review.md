### 4.3 67과 68의 속도가 1.8배 다른 이유

- **[확인]** 68은 출력 토큰이 42% 적었는데도 출력 시간이 더 길었습니다. 토큰당 속도가 1.8배 느렸습니다.
- 입력 길이 차이(+20%)만으로는 7.8B 모델에서 이 정도 디코딩 속도 차이를 설명하기 어렵습니다 **[추정]**.
- 가능한 원인 **[추정, 미측정]**:
  1. **GPU/CPU 혼합 실행 또는 자원 경합.** 프롬프트 처리 250~320 tok/s와 출력 5~10 tok/s는 7.8B Q4 모델을 GPU에 다 올렸을 때 흔히 보는 값보다 낮습니다. 일부 레이어가 CPU에서 돌거나, Android 에뮬레이터가 GPU·CPU를 함께 쓰고 있을 수 있습니다.
  2. **JSON 스키마 문법(format) 제약 샘플링 비용.** 68은 place_id enum이 15개(67은 9개)라 문법 상태가 큽니다.
  3. 생성 시점의 다른 프로그램 부하, 발열로 인한 클럭 저하.
- 확인 방법: 생성 직후 `ollama ps`의 PROCESSOR 열(예: `100% GPU` 또는 `40%/60% CPU/GPU`), Ollama 서버 로그의 `offloaded N/M layers to GPU`, 작업 관리자의 GPU 메모리. 에뮬레이터를 끈 상태와 켠 상태를 같은 입력으로 비교합니다.

### 4.4 66이 실패한 이유 [추정]

- 66은 67과 같은 3일·9곳 입력이었습니다. 67 수준의 출력(약 1,200토큰)을 180초 안에 내려면 **약 7.0 tok/s 이상**이 필요합니다((180 − 8.2초) ÷ 1,207).
- 68 수준 속도(5.36 tok/s)였다면 약 233초가 걸립니다.
- 즉 **출력 속도가 초당 7토큰 밑으로 떨어지면 3일 일정은 실패합니다.** 실패는 프롬프트 문제가 아니라 속도 변동의 결과로 보입니다.

### 4.5 요인별 영향 [확인 + 추정]

|---|---|---|
| 출력 토큰 수 | **가장 큼.** 시간의 91~94%가 출력이고 시간은 토큰 수에 비례 | [확인] |
| 토큰당 속도(하드웨어·부하) | 큼. 같은 모델에서 1.8배 차이 | [확인]. 원인은 [추정] |
| 여행일수·항목 수 | 출력 토큰을 늘림(항목당 약 80~88토큰) | [확인] |

| 후보 수(9 → 15) | 프롬프트 처리 +4초 정도. 문법 enum 비용은 [추정] | |

### 4.6 180초 timeout의 적절성

- 현재 속도 범위(5.4~9.7 tok/s)에서 3일 일정은 130~240초가 필요합니다. 180초는 경계선이라 실패가 반복될 수 있습니다 **[추정]**.
- **timeout만 늘리는 것은 해결책이 아닙니다.**
  - 사용자 대기가 3~4분으로 늘어납니다.
  - 앱 연결이 133초에 이미 끊긴 사례(13장)처럼 HTTP 요청이 길수록 불안정합니다.
- timeout은 출력 토큰을 줄인 뒤 실제 분포를 보고 정하는 것이 맞습니다.

### 4.7 num_predict(출력 상한) 위험

- **[확인]** 두 성공 건 모두 `done_reason=stop`이고 사용률은 39~47%입니다. 지금 일정 크기로는 잘림 위험이 낮습니다.
- 다만 상한은 실패를 막는 장치가 아닙니다. 2,560토큰을 5 tok/s로 생성하면 500초가 넘으므로, 상한 안에서도 timeout은 날 수 있습니다.
- 잘림이 나면 JSON 오류로 한 번 재시도하므로 시간이 두 배가 됩니다. `done_reason=length`가 나오는지 계속 봐야 합니다.

### 4.8 안정성과 표본 한계

- 실패율 1/3, 성공 건 소요시간 133~144초입니다. **표본 3건이라 통계적 결론을 낼 수 없습니다.**
- 벤치마크 설계는 17장에 있습니다.

## 8. 동선 및 이동시간 검증

- **이동시간 출처 [확인]**
  - DB와 API: `route_provider=unavailable`이라 모든 `travel_minutes_from_previous`가 NULL이고, API는 `travel_status=UNKNOWN`을 돌려줍니다. 일정 화면은 '이동시간 정보 없음'을 보여줍니다(7.5l). **올바른 처리입니다.**
  - **문제 1 (Critical):** 일정 화면의 '오늘의 여행 보기'는 실제 장소를 넘기지만, 이동시간은 첫 항목 외 모두 `'도보 10분'`으로 고정합니다(`itinerary_screen.dart:1885`).
  - **문제 2 (Critical):** 홈 '오늘의 일정', 프로필 '내 여행 일정', 날씨 화면은 일정 없이 `TodayTravelScreen`을 엽니다. 이때 하드코딩 목업(`today_travel_screen.dart:40~`)의 '도보 5분 / 10분 / 8분'이 그대로 보입니다.
- **같은 관광권역 중복 [확인]:** 68은 광안리 한 권역(반경 약 400m)을 이틀 동안 4개 '관광지'로 나눠 씁니다. 67은 애월해안도로 한 구간 안에서 3일을 보냅니다.
- **실제 이동 가능성:** 67은 거리상 차로 충분히 가능합니다. 68의 저녁 이동(9.9km, 1시간 간격)은 가능해 보이지만 교통 상황은 **검증 불가**입니다.
- **서버 동선 검증 [확인]:** route provider가 없으면 경로 기반 보정(7.5k)과 경로 검증이 모두 건너뛰어집니다. 현재 설정에서는 동선 품질이 전적으로 AI에 달려 있습니다.

## 12. AI 원본 결과와 서버 후처리 분석

원본 AI 응답은 저장되지 않습니다. 아래는 코드와 최종 결과로 구분한 내용입니다.

| 단계 | 누구 책임 | 확인 내용 |
|---|---|---|
| 1. 후보 선정 | **서버** | **[확인] 주요 원인.** `_candidate_places`는 원하는 수를 `max(2, 일수×2)`(3일 = 6곳)로 잡고, DB에 캐시된 목적지 장소가 그 이상이면 Kakao 검색을 하지 않습니다. 제주는 이전 탐색에서 캐시된 애월해안도로 주변 9곳(식당 7)만으로 채워졌습니다. |
| 2. 관심사 순위 | 서버 | CITY 토큰만 반영 |
| 3. 균형 풀 | 서버 | 관광지를 먼저 확보하는 로직이 있지만, 풀에 관광지가 1곳뿐이면 소용없습니다. |
| 4. EXAONE 생성 | **AI** | 식사시간·횟수·점심 규칙 위반, 과도한 체류시간, 같은 권역 반복은 AI 출력입니다(서버는 시간을 바꾸지 않음). |
| 5. JSON 검증 | 서버 | 형식·ID·시간 역전만 검사하고, 식사 규칙은 검사하지 않습니다. |
| 6. 카테고리 보정 | 서버 | 식당 카테고리는 MEAL로, 카페는 PLACE로 강제합니다(`_canonical_item_type`). 67의 MEAL 7개가 이 경우입니다. |

- 프롬프트는 "식당은 점심·저녁 시간에만"이라고 하지만, **"식당은 item_type MEAL로 출력하라"고 명시하지 않습니다.** 그래서 모델이 식당을 PLACE로 내는 것으로 보입니다 **[추정, 원본 응답 없음]**.
- 서버가 MEAL로 바꿔도 **시간은 그대로**입니다. 15:00–17:00 '식사'가 그렇게 만들어졌습니다. 보정 자체가 새 문제를 만들지는 않지만, 잘못된 식사시간을 걸러내지도 않습니다.
- 자유 시간 6개는 AI가 낸 것일 수도, 중복 장소를 서버가 FREE_TIME으로 바꾼 것일 수도 있습니다. 원본이 없어 구분할 수 없습니다 **[검증 불가]**.

## 15. 문제 목록

### Critical

### High
3. 후보 풀 편향: 캐시 우선으로 식당 위주 9곳만 사용, 관광지 1곳 (67)

5. 같은 관광권역 반복, 일자 간 지역 다양성 없음 (67, 68)
6. 생성 133~144초에 실패 1/3. 출력 속도 변동(5.4~9.7 tok/s)에 따라 180초 경계에서 성패가 갈림

### Medium
9. 추천 이유가 항상 같은 문구 (한글 카테고리와 영문 코드 비교 버그)

### Low

16. 진행률 표시 없음 (회전 문구만)

## 17. 추가 검증 항목과 한계

- 장소 실존·영업·폐업, 영업시간: Kakao·관광공사 실시간 조회가 필요합니다(이번 환경에서 차단됨).
- AI 원본 응답: 저장되지 않아 PLACE/MEAL 원본 값과 FREE_TIME의 출처를 확인할 수 없습니다.
- 하드웨어: GPU 오프로드 비율, 에뮬레이터 동시 실행 영향은 미측정입니다.
- 133초 연결 끊김 원인은 미확인입니다.
- 표본 3건이라 실패율과 평균 시간의 통계적 신뢰도가 없습니다.

**벤치마크 설계 (실제 EXAONE 호출, 승인 필요)**
- 입력: 67·68의 후보와 조건을 고정 fixture로 저장(같은 입력 재사용)
- 조건: 현재 설정 / 출력 간소화(A) / 에뮬레이터 끔(B) / 대체 모델(J)
- 횟수: 조건당 fixture 2개 × 5회. 모델을 미리 로딩해 두고 temperature 0
- 기록: tok/s, 출력 토큰, 총 시간, 실패, done_reason, 자동 품질 점검(식사 규칙, 하루 식당 수, 비식당 활동 수, 권역 다양성, 체류시간)
- 예상 소요: 조건 1개당 10회 × 약 2.5분 ≈ 25분, 4개 조건 ≈ 1시간 40분 (현재 속도 기준 추정)
